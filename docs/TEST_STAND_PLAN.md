# Ранняя тестовая сборка — план реализации

Документ описывает, как сделать **P0 — нагрузочный тестовый стенд** из
`docs/TESTING_AND_PERFORMANCE.md`. Это измерительный инструмент, а не прототип
геймплея: его задача — дать числа, по которым выбираются масштаб армии
(`ARMY-017`), дистанция детализации (`GAME-014`) и пороги `PERF-001`.

| --- | --- |

| Git | работа ведётся в ветке `feature/test-stand`, созданной от свежего `main` (`4853aa7`) |

`abob.server.luau` и `print`-заглушки — мёртвый учебный код, его стоит убрать
отдельной задачей.

## 2. Границы задачи

**Входит:**

- абстрактная серверная симуляция бойцов: движение, выбор цели, простой бой, смерть;
- детерминированный посев и фиксированный шаг симуляции;
- телеметрия сервера и клиента;
- воспроизводимые сценарии нагрузки из `TESTING_AND_PERFORMANCE.md` — в той части, которая не требует матча;
- автоматический headless-прогон через Roblox Studio CLI;
- Jest-тесты на всю чистую логику.

**Не входит (P1 и позже):** отряды как объекты с приказами и построениями,
мораль, контрольные точки, ресурс, респаун и развёртывание, лобби, DataStore,
игровой интерфейс. Всё это появится поверх стенда, но не в этой итерации.

## 3. Ключевые технические решения

### 3.1. Абстрактные сущности вместо Humanoid

Сервер хранит бойца как запись в таблице (`id`, `team`, `position`, `health`,
`targetId`, `attackCooldown`) и не создаёт `Model` с `Humanoid`. Причина: на
сотнях бойцов `Humanoid` и физика съедят почти всё время кадра, и мы измерим
стоимость движка, а не собственной логики. Клиент рисует бойцов пулом
`Part`-ов (только в визуальном режиме).

### 3.2. Фиксированный шаг, отдельно от кадров

Симуляция идёт шагами по 50 мс (20 Гц). В обычном режиме шаги «догоняют»
реальное время; в измерительном (`compute`) шаги выполняются подряд, без
ожидания кадра. Тогда объём работы одинаков на любом железе, а числа
сравнимы между прогонами и в CI.

### 3.3. Детерминизм

- свой PRNG с явным seed (`Shared/Sim/Random.luau`), без `math.random`;
- обход сущностей **по возрастанию id**, а не `pairs` по таблицам-множествам;
- арена фиксированного размера, расстановка задаётся сценарием;
- проверка: после 600 шагов с одним seed состояние даёт одинаковую чек-сумму.

### 3.4. Пространственная сетка вместо перебора всех пар

`SpatialGrid`: клетка 8 studs, поиск цели в радиусе 40 studs по клеткам вокруг.
Иначе LOAD-C/D на 1000+ бойцов превращаются в O(n²) и меряют не то.

### 3.5. Сервер авторитетен

Клиент только отображает снапшоты и интерполирует движение. Ни попадание, ни
урон, ни смерть клиент не подтверждает (`TECH-001`, `TECH-002`).

### 3.6. Один и тот же код в плейсе и в тестовом месте

Стенд живёт в `src/` и включается флагом (атрибут `ServerScriptService` или
Отдельный `*.project.json` не нужен: `test.project.json` уже переносит весь
`src` в `ReplicatedStorage.Project`, и headless-скрипт может загрузить те же
модули.

## 5. Модель симуляции

- **Спавн.** Две команды, две линии друг напротив друга, прямоугольная
  расстановка `rows × columns` из сценария.
- **Движение.** Каждый боец идёт к своей цели, пока не войдёт в радиус атаки.
  Простая сепарация от союзников не даёт толпе слипнуться в точку. Позиция
  обрезается границами арены.
- **Бой.** Если враг в радиусе и кулдаун равен нулю — урон и кулдаун. HP ≤ 0 —
  боец мёртв и исключается из активных.
- **Перецеливание.** Мёртвая цель заменяется ближайшим врагом; если врагов нет —
  боец ждёт (счётчик простоя в телеметрии).
- **Наблюдатель зависаний.** Живой боец с целью, который за 5 секунд сместился
  меньше чем на 1 stud, считается застрявшим (критерий из `TESTING_AND_PERFORMANCE.md`).

Все числа — константы в `Config.luau`, без «магических чисел» в коде.

## 6. Сценарии нагрузки

Числа ниже — **стартовая лестница**, а не утверждённые значения: `PERF-001`
открыт, пороги определяются замерами. Сценарий — запись в `Scenarios.luau`,
поэтому лестницу можно менять без правки логики.

| ID стенда | Сущностей | Длительность | Что проверяет | Покрывает |
| --- | --- | --- | --- | --- |
| `LOAD-A` | 60 (2×30) | 60 с | базовая симуляция, движение, бой | `TEST-001` |
| `LOAD-B` | 240 (8×30) | 60 с | движение, поиск целей, бой | `TEST-002` |
| `LOAD-C` | 1200 (40×30) | 60 с | ИИ, поиск целей, масштаб | `TEST-003` |
| `LOAD-E-SYNTH` | 1200 в одной точке | 60 с | массовое столкновение, сеть, бой | `TEST-005` частично |
| `STRESS` | 2400 | 60 с | верхняя граница, деградация | лестница |
| `LEAK` | 20 циклов по 300 | 120 с | очистка объектов и подписок | `TEST-006` частично |

**Отложено до появления матча:** `TEST-004` (все 20 слотов) требует P2,
полный `TEST-005` — контрольных точек, полный `TEST-006` — респаунов и
развёртываний. Это зависимость порядка этапов, а не забытые требования.

## 7. Телеметрия

| Метрика | Источник | Где собирается |
| --- | --- | --- |
| время шага: p50, p95, p99, max | `os.clock()` вокруг шага | сервер |
| переполнения шага (> 50 мс) | счётчик | сервер |
| активные и живые бойцы | состояние симуляции | сервер |
| запросы сетки за шаг, занятые клетки | счётчики в `SpatialGrid` | сервер |
| память сервера, МБ | `Stats:GetTotalMemoryUsageMb()` | сервер |
| память клиента, МБ | `Stats:GetTotalMemoryUsageMb()` | клиент |
| FPS клиента: p1, p50 | дельты `RunService.RenderStepped` | клиент |
| RTT: p50, p95 | клиент отправляет `os.clock()`, сервер возвращает эхо | клиент |
| байты снапшотов в секунду | длина упакованного снапшота (оценка) | сервер |
| ошибки шага | `xpcall` вокруг шага | сервер |
| застрявшие бойцы | наблюдатель из §5 | сервер |

Формат вывода — построчный JSON в лог Studio:

```
STAND_METRIC {"scenario":"LOAD-B","tick":120,"stepMs":1.8,...}
STAND_RESULT {"scenario":"LOAD-B","checksum":...,"p95StepMs":2.1,...}
```

Причина: Studio CLI пишет вывод в файл, и построчный JSON проще собирать в CSV,
чем снимать HUD. HUD остаётся для ручного визуального прогона.

## 8. Автоматизация

`scripts/load-test.ps1` — по образцу `scripts/test.ps1`:

1. собрать тестовое место из `test.project.json`;
2. запустить Studio с `--task RunScript` и скриптом прогона;
3. проверить, что в логе есть `STAND_RESULT`, а не пустой/старый лог;
4. сложить результаты в `load-test-results.csv`, вернуть код ошибки при провале.

`scripts/run-load-test.lua` — прогоняет сценарии, печатает JSON и выходит через
`ProcessService:ExitAsync` (как `run-tests.lua`).

**Важное ограничение:** headless Studio — не реальный игровой сервер. Его числа
годятся для сравнения версий между собой (регрессия), но не как обещание FPS.
Абсолютные замеры FPS и памяти клиента — вручную в Studio Play и на реальном
сервере, с фиксацией железа.

## 9. Тесты (Jest Lua)

| Модуль | Что проверяем |
| --- | --- |
| `Random` | одинаковый seed → одинаковая последовательность; разные seed различаются; значения в диапазоне |
| `SpatialGrid` | находит ближайшего; пустая сетка → `nil`; соседние клетки видны; удалённый не находится |
| `Movement` | боец приближается к цели; останавливается на радиусе атаки; не перелетает; не выходит за арену; сепарация разводит совпавшие позиции |
| `Combat` | урон уменьшает HP; кулдаун блокирует второй удар; HP ≤ 0 → смерть; своим урона нет; мёртвая цель заменяется новой |
| `Simulation` | 600 шагов с одним seed → одинаковая чек-сумма; нет NaN; никто не вышел за арену; мёртвые не участвуют |
| `Metrics` | перцентили на известном наборе; пустая выборка; кольцевой буфер не растёт |
| `Scenarios` | ID уникальны; числа и длительности положительны; таблица покрытия не теряет сценарии |
| `Snapshot` | encode → decode даёт исходное состояние |

Тесты пишутся до кода: сначала красный прогон по правильной причине, затем
реализация, затем зелёный. Каждый тест создаёт своё состояние в теле или в
`beforeEach`.

| --- | --- | --- | --- |

## 11. Критерии приёмки

- Сценарий завершается без ошибок, `STAND_RESULT` содержит все метрики.
- Два прогона `compute` с одним seed дают одинаковую чек-сумму.
- После остановки: 0 активных сущностей и 0 подключённых подписок стенда.
- В визуальном режиме клиент не меняет HP и позиции; при остановке сервера
  симуляция стоит (проверка авторитетности вручную).
- `selene src`, `stylua --check src`, `rojo build`, Jest — без ошибок.
- Baseline записан с железом, без обещаний FPS на целевых устройствах.

## 12. Риски

| Риск | Что делаем |
| --- | --- |
| Headless Studio даёт нереалистичные числа | `compute`-режим для сравнений; абсолютные замеры — на реальном сервере |
| Детерминизм ломается порядком обхода или плавающей точкой | обход по id, запрет `pairs` в шаге, чек-сумма в тестах |
| Стенд разрастается в P1 | границы в §2, проверка на ревью |
| Репликация становится узким местом | отдельный замер байтов и режим без репликации |
| Studio CLI капризен | переиспользовать паттерн `test.ps1`: ожидание стабильного лога, проверка сводки, ненулевой код при провале |
| Слишком много сущностей для одного шага | лестница и `STRESS` показывают точку деградации, дальше — LOD |

## 13. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Объём итерации | только P0-стенд: движение, простой бой, телеметрия, сценарии; P1 и позже — следующими итерациями |
| Отображение бойцов | абстрактные капсулы-`Part` из пула на клиенте |
| Мобильные замеры | после PC-стенда, отдельной итерацией |
| Ветка | `feature/test-stand` от свежего `main` |

Стартовая лестница сценариев (60 / 240 / 1200 / 2400 бойцов) остаётся
предложением: числа живут в `Scenarios.luau`, и первый прогон покажет, где
начинается деградация.
